## 2. 任务 0 · 现有能力与接续位置

### 2.1 编排入口

| 环节 | 实际类与接口 | 当前约束 |
| --- | --- | --- |
| 想法草稿 | `TaskIdeaController` `POST /api/task-ideas/draft`、`TaskIdeaService` | 只整理文字，不创建任务、工作区或调用工具；`LOCAL` 规则可离线运行 |
| 入口路由 | `EntryRouteService`、`POST /api/entry-routes/preview` | 只解释规则和候选流程，不授予权限 |
| 任务与首运行 | `RunService.create`、`TaskCreationService.persist`（单事务） | 任务、首运行、计划、预算、入口策略、授权范围和费用上限一起提交；提交后才派发 |
| 计划保存 | `PlanService.initializeWorkflow`、`PlanGraphRepository` | 先核对全部受信引用再写节点；`workflow_plans.run_id` 唯一，**一次运行只有一份计划** |
| 节点认领与交接 | `WorkflowExecutionService.claimWorkflowNode` / `claimWorkflowCheck` | 运行行锁 + 状态条件更新；依赖必须已结算且证据当前 |

| 授权与证据 | `WorkspaceAuthorizationService`、`AuthorizedFileSet`、`WorkspaceService` | 目录展开、排除、撤权和字面路径差异；工具调用时再次校验 |
| 交付观察 | `ExecutionViewService`、`ExecutionFlowPanel`、`RunOutputsPanel` | 节点/尝试/交接/检查/费用/快照；文件交付按成功写入回执投影 |

### 2.3 工作区初始化与检查点

- `POST /api/workspaces` 从现有仓库创建隔离分支；`POST /api/workspaces/from-idea` 创建带空白已跟踪文件的独立工作区（1 至 5 个简单文本文件）。两者都沿用同一套 Git 隔离和授权规则。
- `workflow_checkpoints` 只在已结算节点边界保存；`RunSnapshotService` 校验计划版本、预算摘要、边界摘要和工作区指纹；`recovery_leases` 处理未过期拒绝、过期接管和释放。
- 写入恢复仍沿人工核对边界，不自动重放可能已经产生的文件变更。

### 2.4 独立审查与单计划约束

- `PlanService.requireIndependentReview`：每个写入节点必须有一个直接依赖它、且不读取工作区的 REVIEWER 节点；写入模板缺少独立审查时计划保存失败。
- `workflow_plans.run_id` 唯一，`plan_adjustments` 只在同一运行内递增版本；运行中换图不在本期范围。

## 3. 任务 1 · 候选计划

### 3.1 数据与协议

| 项目 | 实现 |
| --- | --- |
| 协议版本 | `PlanCandidateDraft.PROTOCOL_VERSION = 1`；未知版本拒绝 |
| 模型字段 | `schemaVersion`、`nodes[]`（`key`、`title`、`role`、`objective`、`dependsOn`、`readFiles`、`writeFiles`、`expectedOutputs`、`acceptanceCriteria`）、`assumptions`、`openQuestions` |
| 角色 | `ANALYZE` → `workspace-analysis` v1、`IMPLEMENT` → `workspace-edit` v1、`REVIEW` → `workspace-change-review` v1 |
| 输入快照 | `PlanCandidateInput`：目标、入口、工作区、写入授权、文件白名单、约束、验收条件、交付物；生成时冻结 |
| 摘要 | `plan-input-v1` 输入摘要；`plan-candidate-v1` 覆盖协议、输入摘要、稳定拓扑顺序的节点、依赖、文件、产出、验收条件和角色映射的定义摘要（含技能内容） |

### 3.2 校验规则

1. 协议版本为 1，节点 1 至 8 个；节点键小写字母开头、最长 32 位且唯一。
2. 依赖必须存在、不能自依赖或重复；按模型顺序做稳定拓扑排序，有环即拒绝。
3. `writeFiles ⊆ readFiles ⊆ 任务授权文件`；路径按 `AuthorizedFileSet` 规范化，拒绝越界、Git 元数据和重复项。
4. 两个开发节点的写集合互斥；ANALYZE 不能写文件；REVIEW 读写集合都为空。
5. 每个 IMPLEMENT 至少写一个文件，并声明至少一个必需 `FILE` 产出；文件产出路径必须属于该节点写集合；TEXT 产出不带路径。
6. 每个 IMPLEMENT 都有直接依赖它的 REVIEW；至少一个最终 REVIEW 直接依赖全部 IMPLEMENT。
7. 角色映射的受信定义必须存在、权限角色匹配，且非 IMPLEMENT 定义不得包含写入工具。
8. 验收条件 1 至 10 条、每条不超过 300 字；预期产出 1 至 5 项；假设与待确认事项各不超过 10 条。
9. 通过校验才计算候选摘要；失败逐条返回节点、文件或依赖位置，不自动修补图。

### 3.3 状态与入口

| 项目 | 实现 |
| --- | --- |
| 生成 | `POST /api/plan-candidates`，接收 `requestId`、输入快照和可选 `previousCandidateId`；立即返回 `GENERATING` |
| 读取 | `GET /api/plan-candidates/{id}`；`GET /api/plan-candidates?groupId=...` 查看同组历史 |
| 取消 | `POST /api/plan-candidates/{id}/cancel`；只对生成中生效 |
| 状态 | `GENERATING → READY / INVALID / FAILED / CANCELLED / INTERRUPTED / STALE / CONSUMED` |
| 幂等 | 同归属同 `requestId` 同输入返回原候选；同标识不同内容返回 409 |
| 组与版本 | 首次生成以输入指纹为组；带 `previousCandidateId` 重新生成沿用组并递增 `inputVersion`；同组旧 READY 立即 `STALE`；晚到的旧版本结果也结算为 `STALE` |
| 中断 | 应用启动时把上一个进程遗留的 `GENERATING` 标记为 `INTERRUPTED` |
| 执行归属 | `ExecutionScope(ownerScopeKey, actorKey)` 固定 `LOCAL`，由 `ExecutionScopeResolver` 从服务端解析；候选按 `owner_scope_key` 查询 |

### 3.4 持久化

`plan_candidates` 保存归属、组、输入版本、请求标识、来源候选、协议版本、输入与候选摘要、输入与候选 JSON、状态、错误原因、模型名和 Token 用量、创建与结算时间。唯一约束 `(owner_scope_key, request_id)`；组索引 `(group_id, input_version)`。模型消耗只记在候选行，不写入执行节点的模型调用。

### 3.5 页面

- `PlanCandidateDialog` 复用现有 `RunTraceGraph` 显示草稿图，逐节点展示目标、依赖、读写范围、预期产出和验收条件。
- 生成中可取消，失败/无效显示具体原因，可基于上一候选重新生成。
- 入口：
  - 从想法创建任务：代码入口且确认了独立交付文件时可打开；
  - 完整任务表单：代码入口、已有工作区、允许写入、填写授权文件和验收条件后可打开。
- 页面明确显示「只生成并校验候选计划，不创建任务、运行或写入授权」，并提示规划调用会把已确认输入发送给 DeepSeek。
