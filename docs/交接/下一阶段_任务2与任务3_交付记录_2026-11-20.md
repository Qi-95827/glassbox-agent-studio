## 2. 任务 2 · 确认并物化运行

### 2.1 确认绑定

`POST /api/plan-candidates/{id}/runs` 接收 `expectedCandidateSha256`、`expectedInputSha256`、`expectedInputVersion`、`modelMode` 和可选费用预算。

- 确认前复核：候选必须是 `READY`；候选摘要、输入摘要和输入版本与保存值一致；该候选仍是同组最新输入版本；已有工作区基线与文件版本未变；候选在当前 Agent 定义和规则下重新校验后摘要仍一致。
- 创建事务内锁住候选行并再次复核，然后物化任务、运行、计划、节点规格、授权范围和确认事件，再把候选改为 `CONSUMED` 并写入 `run_id`。
- 重复确认返回同一运行，不创建第二个任务，也不再派发。
- 事务提交后才派发；创建失败不会留下已派发但缺少计划或授权的运行。

### 2.2 独立工作区

- 已有工作区直接复用；独立交付在确认时创建空白工作区。
- 用 `PREPARING → READY/UNKNOWN` 条件更新保证同一候选只有一个请求能创建工作区；结果未知时保留状态等待人工核对，不自动创建第二个工作区。

### 2.3 节点级文件范围

- 新增 `plan_node_specs`：保存每个节点的 `read_files_json`、`write_files_json`、产出契约、验收条件和规格摘要；规格摘要绑定候选摘要。
- 计划图使用 `workflow-graph-v6`，在 v5 字段后绑定每个节点的规格摘要；持久化规格被改写时执行停止。
- 执行前按任务当前授权复核 `readFiles ⊆ 文件授权` 与 `writeFiles ⊆ readFiles`。
- `AgentExecutionRequest` 增加节点写入子集；装配计划按读取数量和写入数量分别选择工具契约；`AgentToolContext` 与工具注册表对读取、搜索使用读取集合，对写入使用更窄的写入集合。
- 历史模板没有节点规格时继续使用任务级文件范围，行为不变。

## 4. P07/P08/P14 收口

### P07 · 必需产出缺失不能进入审查

- `finishWorkflowNode` 结算开发节点前，对比节点规格的必需文件与该实例成功写入回执中的路径；缺失时节点失败、运行 `BLOCKED`（`STOP_CAUSE=OUTPUT_MISSING`），审查节点不会启动，已写入文件和调用证据保留。
- 反例 `MissingRequiredOutputIntegrationTest`：页面节点故意不写 `index.html`、`style.css` → 运行 `BLOCKED`，原因包含「缺少必需产出」和缺失路径；审查没有 Agent 实例、没有接收交接；`sort.js` 写入保留；交付投影的页面节点缺文件，未验证项包含缺失路径。

### P08 · 交付正文的服务端校验

- 新增 `GET /api/runs/{id}/delivery/files?path=...`：路径必须出现在该运行的成功写入回执中；读取前复核任务当前有效授权；当前 SHA-256 与回执一致才返回正文。版本变化时返回 `currentMatches=false`、`content=null`，保留历史回执摘要。
- 目录撤权后，即使文件内容未变，正文接口返回 403；交付投影仍保留历史回执，页面显示「当前文件版本已变化」或授权拒绝原因。
- 交付说明页面改用该接口；摘要不一致时不再展示工作区新版本正文。
- 反例 `BubbleSortDeliveryIntegrationTest` 末尾：`sort.js` 正文可读；修改文件后同一接口返回不一致且无正文、回执摘要不变；`style.css` 仍可读；未写入的路径被拒绝；HTTP 入口同样校验。
- 反例 `DeliveryRevocationIntegrationTest`：保持文件内容不变，撤销覆盖 `src/a.txt` 的 `src` 目录授权 → 正文接口 403、历史回执仍在；未撤销的 `docs/keep.txt` 仍可读。
- 浏览器下载：在工作台交付说明展开 `sort.js` 点「下载文件」，浏览器实际下载 872 字节，落盘文件 SHA-256 `631e81a481da039489b424738bdc37be1494df133627c69e8886378ac3ad944f`，与写入回执一致。

### P14 · 独立工作区准备中断后的收口

- 同一候选使用稳定的 `workspace_operation_id` 决定仓库目录 `idea-<id>`，`preparation_id` 是租约持有者；接管只更换租约持有者，目录标识保持不变。
- 目录用 `Files.createDirectory` 原子创建，只有成功创建目录的请求可以执行 Git 初始化；并发请求不会同时初始化同一目录。
- `PREPARING` 在 60 秒租约内视为活跃操作，其他确认等待而不是接管；超过租约才允许按预期的 `preparation_id` 接管。接管、结算和标记 `UNKNOWN` 都带 `preparation_id` 条件，旧请求恢复后不能覆盖新状态。
- 已登记工作区按稳定目录标识核对并复用；目录存在但未登记或结果未知时转 `UNKNOWN`，等待人工核对；目录不存在才创建。
- 运行创建失败时候选保持 `READY`，重试复用已准备的工作区，只创建一个运行。
- 反例 `PlanCandidateRunIntegrationTest`：
  - `interruptedPreparationAfterGitIsReconciledByOperationId`（Git 完成、候选未记录，确认时复用同一工作区，目录标识不变）；
  - `runCreationFailureAfterPreparationReusesWorkspaceOnRetry`（注入运行入库失败后重试，工作区数量不变）；
  - `concurrentConfirmationWaitsForActivePreparationAndCreatesOneRun`（租约内第二个确认等待，不接管；放行后 1 个工作区、1 个任务、1 次派发、同一运行）；
  - `leaseExpiryTakeoverKeepsSingleWorkspaceRunAndDispatch`（第一个请求登记工作区后暂停，租约过期由第二个请求接管并完成；旧请求恢复后结算被拒绝，最终仍只有 1 个工作区、1 个任务、1 次派发）。
