# 任务 8 · 业务持久化层 JPA 迁移（第一批）交付记录

> 日期：2026-11-19。范围：把「创建任务 → 创建首运行和初始计划 → 保存入口策略及其他必需业务记录 → 提交后派发」闭环迁到 Spring Data JPA / Hibernate，同时保留并发、顺序和条件更新所需的参数化 SQL。未开始其他业务读写批次。

> 本记录描述首批交付时的混合实现。后续工程规范与迁移顺序以[代码开发规范第 8 节](../开发规范/代码开发规范.md#8-统一使用-spring-data-jpa)和[持久化统一迁移](动态Agent重构后_产品开发与验收交接.md#持久化统一迁移)为准。

## 1. 业务条件

1. 任务、首运行、初始计划（计划头、节点、依赖）、角色/工具预算、入口策略、Bug 接收记录和创建事件，要么全部提交，要么全部不可见；不能留下可派发的半成品。
2. 只有创建事务提交成功后，运行才能进入执行队列；待确认计划在用户批准前不派发。
3. 同一次业务写入中的 JPA 与 JDBC 使用同一个数据源和同一个事务，由服务层统一控制提交。
4. 旧 H2 库可以启动并读取历史任务、运行和事件；Hibernate 不建表、不改表，表结构仍由 `schema.sql` 维护。
5. 事件仍按运行内 `run_seq` 排序和分页，晚提交事件不会被旧游标漏读。
6. AgentScope 自己的 `agentscope_*` JDBC 状态表保持独立，不进入业务 JPA 实体和迁移。

## 2. 权威记录与事务边界

- **唯一创建提交边界**：`TaskCreationService.persist`，`@Transactional`。
- **事务管理器**：Spring Boot 因 JPA 自动使用 `JpaTransactionManager`；`JdbcTemplate` 在活动事务中取得同一连接。`TransactionTemplate` 内部写入加入外层事务，不单独提交。
- **派发点**：`RunService.create` 在 `persist` 返回（提交成功）后调用 `dispatchInitial`；`reviewPlan=true` 时不派发，`approvePlan` 提交后再派发。
- **JPA 实体**：`dev.workbench.persistence.entity`，与 `TaskDefinition`、`RunSnapshot` 及接口 `Map` 返回结构分开。
- **JPA Repository**：`dev.workbench.persistence.jpa`。
- **表结构**：`backend/src/main/resources/schema.sql`；`spring.jpa.hibernate.ddl-auto=none`。
- **AgentScope 状态**：`AgentStateConfiguration` 继续使用官方 `JdbcAgentStateStore`，不经过业务 JPA。

## 3. 失败后状态

- 入口策略保存失败发生在任务、运行、计划和创建事件已写入之后；外层事务回滚，上述记录全部不可见，派发计数不增加。
- 修复后重试会生成新的任务/运行 ID，恰好得到一套任务、运行、计划和策略记录，创建事件一条。
- 派发线程池拒绝仍走原有 `RejectedExecutionException` 路径，保留可查看的失败运行；该路径不属于本次事务改造范围。

## 4. 已迁移到 JPA 的读写

| 表/用途 | 写入或读取 | 位置 |
| --- | --- | --- |
| `tasks` 任务行 | 创建任务插入 | `RunRepository.createTask` → `TaskEntity` + `TaskJpaRepository` |
| `task_role_budgets` | 创建时写入角色预算 | `TaskRoleBudgetEntity` + `TaskRoleBudgetJpaRepository` |
| `task_tool_budgets_v2` | 创建时写入工具预算 | `TaskToolBudgetEntity` + `TaskToolBudgetJpaRepository` |
| `runs` 首运行及恢复运行 | 创建运行插入 | `RunRepository` 私有 `createRun` → `RunEntity` + `RunJpaRepository` |
| `workflow_plans` | 计划头插入、图摘要更新、按运行读取 | `PlanGraphStore` + `WorkflowPlanEntity` / `WorkflowPlanJpaRepository` |
| `plan_nodes` | 初始计划节点插入 | `PlanRepository.initialize` / `initializeWorkflow` → `PlanGraphStore.saveNode` |
| `plan_node_dependencies` | 初始依赖边插入 | `PlanRepository.saveEdges` → `PlanGraphStore.saveEdge` |
| `task_entry_policies` | 保存与按任务读取 | `EntryPolicyService` + `EntryPolicyEntity` / `EntryPolicyJpaRepository` |

JPA 写入后需要被同一事务中的 JDBC 立即读到时（计划头外键、运行行锁、事件锁），显式调用 `flush()`，避免 Hibernate 延迟到提交才插入。

## 5. 保留的参数化 SQL 及保障的行为

| 位置 | 保留的 SQL | 保障的行为 |
| --- | --- | --- |
| `RunRepository.insertEvent` | `SELECT id FROM runs WHERE id=? FOR UPDATE`，再取 `MAX(run_seq)+1` 并插入事件 | 同一运行的事件按提交顺序编号；持锁事务提交前其他写入不能分配更晚序号。读取方只用 `run_seq` 游标，晚提交事件不会落到旧游标之前。 |
| `EventQueryService.page` | `run_seq > ? ... ORDER BY run_seq LIMIT ?` | 增量分页不漏读、不重复，不混入其他运行；游标不是全局自增 ID。 |
| `ExecutionViewService` 事件与快照 | 按 `run_seq` 读取最大序号和结构化事件 | 流程图断线重连以持久化事件为准，不按节点顺序推断。 |
| `RunRepository.update/finishReviewedRun/finishStoppedRun` | `UPDATE ... WHERE id=? AND status=...` 等条件更新 | 终态不被晚到结果改回；取消、失败、完成只接受合法起点。 |
| `PlanRepository.start/startCheckNode/finishCheckNode/finish/requeueFailedNode/attachRecovery` | 带节点状态和计划版本条件的原子更新 | 同一节点/检查只被认领一次；恢复复用不覆盖历史。 |
| `WorkflowExecutionRepository.claimWorkflowCheck` 等 | `SELECT ... FOR UPDATE` 与条件更新 | 系统检查、尝试和交接在并发下只认领一次。 |
| `WorkflowRecoveryRepository.recover`、`TaskSupplementService` | 运行/任务行锁和状态条件更新 | 恢复与补充只在核验边界内推进，过期版本被拒绝。 |
| `RunRepository.setTaskArchived`、`taskVersion` | 简单更新/读取暂时保留 SQL | 归档沿用原有行为；任务版本乐观校验不变。下一批再迁移。 |

## 8. 配置与兼容

- `pom.xml` 增加 `spring-boot-starter-data-jpa`。
- `application.properties` 增加 `spring.jpa.hibernate.ddl-auto=none`、`spring.jpa.open-in-view=false`。
- `WorkbenchApplication` 增加 `@EntityScan("dev.workbench.persistence.entity")` 与 `@EnableJpaRepositories("dev.workbench.persistence.jpa")`；不扫描 AgentScope 状态包。
- 未新增业务表，未改变 `schema.sql` 的迁移方式，未修改既有接口字段。
- `RunRepository.createTaskAndFirstRun` 保留原签名，生产创建路径统一由 `TaskCreationService` 调用；测试中的直连写入仍可用。
