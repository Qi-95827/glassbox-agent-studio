## 1. 登录成功后被 401 踢回登录页（P1）

### 根因

- 登录成功会由 `AuthService.loginSession` 调用 `http.changeSessionId()` 更换 Session ID。
- 浏览器登录成功后，首屏同时发出 `/api/tasks`、`/api/workspaces`、`/api/entry-policies`、
  `/api/entry-routes/preview` 等请求。服务端在首个认证请求上再次完成 Session 轮换；
  与它并发的请求仍携带旧 Session ID，短时间返回 401。
- 旧实现把**任意** 401 都当成会话失效并立即清空登录态；自动发出的规则预览 POST
  只要在其中，就会把已经正常显示的工作台踢回登录页。
- 同时，旧 `ensureCsrf` 缓存的 token 可能属于轮换前的匿名 Session，存在跨会话复用风险。

### 修改入口

- `src/api/client.js`
  - 401 先调用单飞 `recoverSession()`（最多 3 次、间隔 140ms 确认 `/auth/status`），
    仍有用户时用新 Cookie 重试原请求一次；确认无用户才触发登出。
  - CSRF 增加 epoch；`resetCsrfToken()` 使轮换前仍在途的 token 结果失效。
  - 403 CSRF 失效仍保留一次刷新重试。
- `src/features/auth/AuthGate.jsx`
  - 登录/初始化成功后取消旧的 auth-status 查询，先发一个认证 GET 触发 Session 轮换，
    再读取 `/auth/status` 确认用户后才渲染工作台；清除旧密码并失效任务缓存。
- `src/api/auth.js`：登录/初始化/登出后重置 CSRF。

### 定向验证

- 干净数据库 `Temp/opencode/wb-clean` + 干净浏览器初始化管理员：工作台正常；首屏
  `/api/entry-routes/preview` 返回 **200**；无 401 控制台错误。
- 已有账号登录：`/api/tasks` 200、规则预览 200，不再出现“工作台一度显示后跳回登录”。
- 刷新运行页/工作台后仍保持登录。
- 重启后端使内存 Session 真正失效后刷新：页面正确回到登录入口。
- 修复前复现记录：登录 200、状态 200 后 `/api/tasks` 401，页面跳回登录。
