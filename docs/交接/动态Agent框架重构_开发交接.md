## 3. 用户的目标

项目是一个面向个人开发者、用于学习和实践的可视化代码开发 Agent。用户希望借助已有的 AgentScope Java 能力，建设**可组合、可观测、有控制边界的多 Agent 系统**。

本次需要一起完成两件事：

1. 将写死的分析、开发、审查角色和固定流程重构为**受控的 Agent 定义、任务计划、节点、独立实例、顺序调度和结构化交接**。
2. 将后端生产 Java 源码逐步归入一个根目录 `backend/src/main/java`，在其中按 Agent、工作流、记忆、工具、控制、业务、基础设施等职责分包。两个前端应用各自保留源码目录。

一个典型目标流程为：接收任务及授权 → 选择受控模板 → 生成并保存计划与依赖 → 按依赖顺序执行节点 → 在节点中装配 AgentScope 实例与授权组件 → 记录实际结果、证据和交接 → 展示计划与执行状态。

首期以受控模板为主；计划保存后，普通任务可根据策略自动执行。只有用户要求计划审阅或策略要求审批时才等待，不能把“计划可以查询”误写成用户一定已经看过。详细定义以重构概要设计第 6、7 章为准。

## 4. 本次完成后应达到的效果

### 4.1 多 Agent 和可组合能力

- 区分任务、运行、计划版本、阶段、节点、节点尝试、Agent 定义和实例；分析、实现、审查是流程中的职责或用途，不再是调度器里唯一允许的固定 Agent 分类。
- 一个 Agent 定义可以被多个节点引用；同一运行中两个节点可引用相同定义，各自产生独立尝试、实例和会话记录。节点可以是 Agent 或系统支持的其他类型，不能为未执行的节点虚构 Agent。
- 按定义和授权组合模型、上下文来源、项目记忆、Skill 与工具列表；缺少必要组件或版本不兼容时明确拒绝，不静默替换或扩大权限。
- 继续复用 AgentScope 实现 Agent 调用、消息和已接入的框架能力；项目负责计划、身份、授权、预算、节点调度、上下文、证据、记录和验收，不再自造另一套推理框架。
- 有一个实际可运行的扩展示例：使用已有组件添加一种受控 Agent 定义，加入工作流节点并执行，证明不需要新增一个硬编码角色分支。配置或注册可采用本次实际实现的受信方式；不要求实现用户可视化自由编辑器。

### 4.2 必须贯穿的控制

- 每个实例都绑定真实任务与节点归属、身份／授权、预算、停止控制和必要事件；记忆、工具和 Skill 等业务能力可以按需配置，但基础控制不可因为组件未配置而消失。
- 现有工具保持兼容，实际调用必须经过可实施授权、参数校验、预算、取消和记录的受控路径；如果某种接入无法保证，应拒绝开放。此次不新增具体 Git、文件、测试等业务工具。
- 节点状态、每次尝试和实例生命周期分开记录；重试保留旧尝试与累计消耗；取消后的晚到回调不能把运行重新改成进行中。
- Agent 之间以结构化交接传递目标、约束、事实、推断、未决问题和经授权的证据引用；保留来源，缺少的历史字段保持未知。
- Checkpoint 是 Agent 系统内部状态，不等于 Git 提交。保留已支持的安全恢复边界；执行中会话、写入或外部结果未知等场景不能声称已经安全恢复或端到端恰好一次。
- 用户可查看计划图、节点状态、实际 Agent／工具调用、消耗、交接和结果；计划节点与实际调用次数分开，未知用量、未执行和失败不得冒充成功。

### 4.3 测试与验收

以[重构概要设计第 12 章的 A01—A26](../概要设计/动态Agent与可组合工作流_重构概要设计.md) 和第 16 章整体验收为准。重点覆盖：

1. 计划先保存再执行；只读任务不会凭空获得写入能力。
2. 两个节点使用同一 Agent 定义时，实例、会话、输入与结果独立；前置节点失败时下游不伪装为已完成。
3. 未授权工具、缺失或不兼容组件、超预算、取消、晚到结果与工具结果未知均按契约处理。
4. 新交接可追溯节点、实例及证据，旧交接和已支持旧数据按兼容方案读取。
5. 支持的 Checkpoint 恢复保留消耗；不支持的场景明确拒绝或要求核对。
6. 用户视图和指标来自真实记录；生产 Java 编译只依赖新的后端源码根；旧入口、资源及前端构建正常。

测试集中在每个迭代／有意义的批次结束时进行，不需要每移动一个文件都跑全量测试。关键边界允许必要的针对性检查；最终执行与改动匹配的构建、回归及验收并报告失败和跳过情况。历史记录中的测试数字仅为当时结果。

## 6. 实施顺序

执行范围为重构概要设计第 16 章的**批次 0—5**，这些批次是同一次重构的内部顺序，不是要求额外发布新产品版本：

1. **基线与清点**：保护未提交工作，核对旧行为、数据、构建与测试。
2. **领域和兼容**：定义、计划、节点、实例、版本、底座与旧固定流程兼容。
3. **装配和交接**：AgentScope 适配、组件注册与快照、上下文／记忆／工具、结构化交接。
4. **计划和调度**：先持久化计划，再执行受支持的顺序图；分离节点、尝试与实例状态。
5. **控制和恢复**：预算、工具网关、取消、暂停及受支持的 Checkpoint；迁移现有业务和存储时保持事务。
6. **观测、评测与收尾**：计划图、轨迹、真实指标、A01—A26 相关验证，完成源码根统一与兼容检查。

根据依赖关系可以调整批次内部的小步顺序，但不能把源码结构重构排除出本次交付；每个批次的详细目标与退出条件仍以概要设计为准。

## 7. 后续能力：保留扩展边界，不冒充实现

本次要让框架能继续扩展，但不要为下面每一项提前堆空类，也不要把接口存在当成能力已完成：

- 模型自由生成计划、用户拖拽编排、运行中修改计划及任意插件热加载。
- 并行多 Agent、并发写入、跨进程租约、共享预算原子预留。
- 自动长期记忆、语义检索、完整压缩／遗忘和数据删除传播。
- 任意位置会话恢复、周期一致性快照、外部动作自动对账或回滚。
- 完整身份认证、多租户共享部署、运营后台、自动告警平台。
- 新的具体 Git、测试、文件或第三方平台工具；保留现有工具及其约束即可。

对应的注册、组件版本、上下文来源、工具网关、节点执行、恢复判定、事件与评测等**必要契约需要有明确输入输出和不支持时的行为**。首期必需路径应有真实实现与测试。

## 8. 迁移和开发注意事项

1. **先理解既有代码，再迁移。** 保留当前未提交／未跟踪工作；不要用 Git 重置、清理或覆盖来获得所谓干净工作区。
2. **不只移动文件。** 大类要按责任逐步拆分；Spring 扫描与注入、包可见性、事务、数据库迁移、旧序列化格式、事件、前端 API 和测试同步适配。
3. **不要破坏权限与数据。** 用户授权列表、历史记录、模型配置、工作区与 Checkpoint 应按原契约兼容。恢复和数据库迁移必须考虑中断、版本不兼容和未知结果。
4. **保护本地密钥。** 用户已有本地 DeepSeek 配置；不要读取、打印、上传、复制或提交 API Key。自动测试优先使用模拟模型；真实模型验证须遵循用户授权及项目的数据外发边界，说明可能产生费用。不要把真实模型效果或用量写成已验证，除非确实执行。
5. **避免无关的目录清理。** 此前递归删除临时测试目录曾被执行策略拦截；测试优先使用隔离、可控路径，测试结束先停止服务，不反复尝试同一类被拦截的递归删除；需要保留时如实记录。
6. **遵守代码规范。** 有意义的类、关键方法、字段及复杂逻辑使用准确的中文注释；稳定受控状态用枚举，标识、时间、数量等使用合适类型，不能把所有字段都做成 `String`。Java 使用项目约定的 Google Java Format 风格。
7. **UI 暂以功能为主。** 用户对现有页面视觉不满意，已记录后续优化需求；这次只做计划和运行过程展示所必需的调整，不擅自扩大成视觉重做。
8. **数据可信度。** 模型输出是待验证内容；不把模型的“已完成”当作测试通过，也不将模拟工具、模拟 Bug、计划节点或未知 Token 计数表述为真实成功。
