## 3. 所有新功能共用的可视化约定

- **计划图与实际执行叠加。** 计划和依赖来自已保存的计划版本。计划级接收、待确认、暂停和最终交付显示在图的两端或运行状态区；业务节点由计划生成。正在执行的节点突出显示；检查、Agent 和后续人工关卡采用不同类型。
- **节点内显示已记录的动作。** 模型请求、读取、搜索、写入、检查和交接能下钻到实际记录。尝试与 Agent 实例单独标识，重试保留上一条失败；系统检查无 Agent 实例时留空。模型结论与证据来源分别展示，界面不暴露模型隐藏推理或凭据。
- **状态能回答用户下一步。** 说明为什么阻塞、哪些下游未启动、现在允许什么操作。已排队、待审批、在途、受限、失败、取消、跳过、结果未知和历史复用清楚可辨。服务端未记录的原因显示未记录，不从节点顺序或日志文案猜。
- **扩展靠数据契约。** 新模板和 Agent 定义使用同一个图。新增类型通过通用状态、摘要、证据引用及操作描述接入；专用详情可按类型扩展。前端不按模板名或角色名编排执行，也不参与授权决策。
- **记录关联可复验。** 请求、事件和证据通过稳定的运行、计划、节点、尝试、检查及调用 ID 关联。读取按归属和权限过滤。刷新或重连从持久化数据重建；子运行复用只引用受控来源，实际新增调用与继承消耗分别计数。

### 任务 1 · 把执行流程图做成任务详情主视图

**起点**为 `WorkbenchController`、`framework/event/`、`PlanRepository`、`WorkflowExecutionRepository` 和 `frontend/user-workbench/src/features/workflows/WorkflowPlanPanel.jsx`。实际契约以[可视化与接口设计](../概要设计/任务执行流程可视化与接口设计.md)为实施依据。

1. **运行投影。** 从计划、节点、尝试、调用与检查的持久化记录聚合 `GET /api/runs/{id}/execution-view`，包含计划版本、节点、依赖边、活动焦点、阻塞、可用操作和恢复来源。将大体积节点详情移到 `GET /api/runs/{id}/execution-view/nodes/{nodeId}`，原接口继续可用。
2. **事件关联。** 在事件读取中增加可校验的计划、节点、尝试、检查及调用引用。首次加载取得当前快照，运行中用游标补取；断线保留旧图并标注更新时间，重连后收齐事件再对照快照。窗口切换或响应乱序时不得污染其他运行。旧事件缺结构化归属时显示在运行层。
3. **工作台入口。** 新建任务得到运行 ID 后打开流程图。主视图展示阶段、节点、依赖和当前动作，点选节点展开输入、尝试、装配摘要、检查、证据、耗时和用量。接入已有审批、暂停、继续、取消和恢复；小屏或键盘用户仍能查看依赖和状态。以真实接口驱动页面。
4. **通用扩展。** 用同一个组件跑双视角汇合、只读检查和模拟 Bug 多阶段。检查失败、预算耗尽、限流重试和恢复都从真实记录投影。新增一个受信模板需要保存节点及依赖，复用现有节点类型时即可进入流程图。

**完成标准**包括以下可观察结果。

| 操作 | 验收结果 |
| --- | --- |
| 创建需确认的任务并观察执行 | 确认前图可查看且没有实际调用；确认后能定位当前节点与实际动作，完成时图和调用账本一致。 |
| 模拟 Bug 正常执行与检查阻塞 | 正常可逐节点追到检查、分析、读取、授权修改、回归和审查。失败时清楚显示阻塞原因、证据与未启动的下游。 |
| 模型限流重试、取消或预算停止 | 同一节点保留多次尝试与累计消耗，失败或未执行有独立状态，晚到结果不把终态变回运行中。 |
| 刷新、断网重连、切换历史运行 | 图和事件与实际查询一致，分页事件无漏读、无重复，旧请求不会覆盖当前运行。 |
| 打开恢复子运行与旧历史 | 子运行能跳转父运行与检查点，复用和实际新调用可区分，历史缺失字段明确显示。 |

交付必须有实际浏览器和 API 对照证据。按「后端数据与事件 → 主视图和控制 → 异常与恢复」推进，完成一个闭环再集中回归。

**任务 1 历史审查项**。下列两项已修复并补测，后续如涉及相同边界可复用。

1. 恢复子运行的继承工具次数与实际恢复口径一致。检查点旧列 `tools` 恒为零，恢复以 `tool_calls` 读到实际值。复用同一权威读取方式，验证 A15 样本显示「继承工具 1 次、本运行新增工具 0 次」。
2. 同一运行的增量事件不能因较小 ID 晚提交而永久漏读。事件的游标顺序要与对客户端的可见顺序一致；重连超过一页时，补齐积压后才标为同步完成。验收覆盖同一运行两个事务提交顺序反转、超过 200 条积压、无漏读无重复和切换运行。

本次任务 1 的完整模拟 Bug 成功路径由 Docker 集成测试覆盖，浏览器抽验覆盖检查阻塞。后续任务实际验证见各自交付记录。

### 任务 2 · 等待补充信息、任务版本与继续执行

**起点**为 `CreateTaskRequest`、`TaskDefinition`、`RunService`、计划校验及任务 1 的阻塞／操作类型。先以模拟 Bug 的必要环境或目标现象信息缺失为示例。

1. 保存待补充事项、稳定原因、关联任务或节点及任务版本。前端在对应位置列出可回答的问题和合法操作，缺关键条件时不启动相关下游。
2. 用户提交补充时记录旧版本和新版本，校验提交目标版本、当前状态、认证边界和授权。只有新信息满足条件时才进入下一步。目标、范围或代码版本变化时标记受影响的计划、证据与审批。涉及重新规划时优先生成新计划／新运行并关联旧历史。保持已批准计划的原始记录。
3. 将等待、提交、拒绝和继续归到原运行链路。工作台能看见处理结果、当前有效版本和后续会否开始；对不允许继续的情形给明确原因。

**完成标准**是通过页面完成「缺信息 → 阻塞 → 补充 → 重新校验 → 按安全边界继续」。证明未补充前零下游写入，重复或过期提交不会重复调度，修改目标或撤销权限不会复用无效审批。

### 任务 3 · 模拟 Bug 分诊、测试证据与交付

**起点**为 `BugService`、`BugReproductionCheck`、`BugRegressionCheck`、`BuiltInWorkflows`、Bug 证据页面与报告。已有固定 Python 容器流程可作为验收样例。

1. 保存模拟 Bug 原始描述、来源标识、版本和时间，处理相同来源重复提交与变化。区分待补充、未复现、环境不可用、目标现象匹配及其他测试失败。
2. 以受信的结构化证据判定目标现象是否复现，再进入明确授权的修复。回归与审查消费时复核代码指纹、归属和测试目标，保留历史通过与当前过期两种信息。
3. 按同一运行串联目标现象、测试入口与结果、授权变更、回归、审查、用户决定和本地模拟反馈。支持查看事实、推断、未验证项及差异。扩展测试语言或构建入口时分批接入固定、经授权的验证器。

**完成标准**是隔离教学仓库的完整模拟 Bug 真实跑通，并在图中定位每一步的证据。未复现、失败现象不符、环境不可用、过期证据和未授权的运行各有明确结果，均不会凭旧证据放行写入或误报通过。回归通过仍等待用户决定。

### 任务 4 · 人工接手、Git 工作区与交付

**起点**为 `WorkspaceService`、`WorkspaceController`、审批与提交服务、文件工具及既有差异页面。各项依赖最小授权、版本校验和可追溯记录。

1. 实现接手与交还。接手前达到可核验的停止边界，在途动作如实显示；人员改动后记录新工作区版本，复核旧测试、审批和依赖。交还须遵循任务 2 的安全继续规则。
2. 逐项扩展工作区。优先未跟踪文件审查和安全的新建文件，再按使用场景加入目录／排除范围和更广搜索。目录权限必须在执行时校验，清理前显示未提交改动、关联运行及可恢复影响。
3. 完善交付和 Git 状态。区分未提交、本地提交、已推送与已合并；任务历史、筛选、归档、报告与差异可追查实际产物。远程操作作为单独功能，每步必须绑定用户明确同意的目标、当前版本与操作结果，冲突或结果未知转为核对。

**完成标准**是人工修改导致旧测试与审批失效，工作台能展示原因并重新验证。工作区真实差异包括适用的未跟踪文件，未授权路径的操作拒绝且不写入。完成任何新的 Git 动作后，可追到审批、目标版本、结果和冲突状态。

### 任务 5 · 可配置评测、对照与基础后台

**起点**为 `evaluation/`、`observability/`、已有评测中心及运行概况。优先沿用现有工作台入口，后台是否独立构建由后续设计确定。

1. 建立可管理的版本化数据集、评测对象与预算。保留现有固定种子与旧批次；记录样本来源、断言、模型／Agent／工具版本、预算及必要的代码和环境条件。
2. 加入可重复的成功与失败样本，覆盖目标不符、缺信息、取消、超限、越权、环境无效和恢复。由独立可验证的断言判定，实际修复评测可用隔离工作区和确定性测试。样本定义有变更时保存新版本。
3. 批次能查看和取消，可按可比条件比较首次成功、重试、人工介入、耗时和已知用量。失败案例经授权脱敏再加入回归；基础后台提供配置状态和受控异常处理，管理动作有操作者及结果。

**完成标准**是用户能选择版本化样本和评测配置，重复发起并从失败案例跳回同一执行流程图。条件一致可比较，条件变化或环境无效明确不可比；实际故障与审批结果可追溯。

### 任务 6 · 可靠恢复、预算与故障治理

**起点**为 `WorkflowRecoveryRepository`、`WorkflowExecutionRepository`、`RunControl`、工具账本及[0.7 可靠恢复计划](../迭代计划/0.7_可靠恢复.md)。先补现有失败场景，再扩展支持矩阵。

1. 设计每条恢复边界的实际支持条件。优先处理未提交文件保护和已知／未知外部动作的状态核对，再按演练覆盖扩展子运行再次恢复、周期快照和跨进程协调。会话中途恢复需要单独证明框架状态与业务账本一致。任何外部动作无法确认时，保留证据并等待核对。
2. 在工作台显示边界、来源、拒绝原因、已继承消耗和未知动作。审批、权限、计划、文件或证据版本改变后，拒绝过期恢复。演练重复请求、崩溃、损坏快照和晚到结果。
3. 分步补资源治理。先按供应方价格版本计算可解释的费用估算，并保留未知用量；再定义严格 Token／费用限额、并发预留结算、预算追加后的继续条件、失败分类与无进展检测。记录实际生效的预算与停止原因。

**完成标准**是通过故障演练证明支持边界可恢复、额度不归零、历史不被改写、未知副作用不会自动重放。前端能解释每次停止、恢复、核对或不支持的原因。更窄的支持范围以矩阵和反例明确。

### 任务 7 · 安全、观测和个人版发布准备

**起点**为[0.8 安全与观测](../迭代计划/0.8_安全与观测.md)、[0.9 集成候选](../迭代计划/0.9_集成候选.md)、[个人 1.0](../迭代计划/1.0_个人可用版本.md)。

1. 针对实际已开放的文件、运行、报告、模型和验证环境补最小授权、敏感数据控制、报告脱敏、操作审计和越权／注入回归。用户能看清允许外发的数据范围、运行限制和需要人工批准的操作。
2. 把告警与真实运行关联。健康、故障、恢复与用量从已有指标逐步扩展；告警能定位对应执行轨迹并说明影响。后台操作受控并保留影响、原因和结果，界面展示必要的状态变化。
3. 补环境自检、首次接入、安装、升级、备份恢复、版本与回退说明。用干净环境从安装、授权仓库、模拟 Bug 执行图、回归、用户审查到交付报告抽验一遍，覆盖失败、权限失效、预算、取消和已支持恢复。按实际范围确认 0.9／1.0 退出条件。

**完成标准**是个人用户可以按文档启动并完成一条受控模拟 Bug 交付，途中每次关键状态和证据均可见；安装、升级和故障处理有可重复步骤和结果。共享部署和运营能力按原路线另行验收。

| 批次 | 实现步骤 | 完成标准 |
| --- | --- | --- |
| 1. 任务创建、计划与事件 | 将初始图、计划读取和确认、事件写入及游标改为 Hibernate。初始图、节点查询和节点状态更新使用同一套持久化路径，测试直接覆盖生产实现。将入口策略规则与入库映射分开，创建与批准派发纳入提交后触发。 | 同一事务确认计划后读到新状态；待确认无派发，外层事务回滚也无派发。用事先已知的任务、运行主键或独立表计数证明回滚后没有孤立记录，合法重试只写一套。重复主键创建不能改写旧记录。同运行并发写事件及游标分页无遗漏、无重复、无串运行。 |
