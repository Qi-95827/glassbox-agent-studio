# Agent Studio 后端重构剩余四项实施提示词

> 可将下列内容连同原始审核文件 `code_artifact.md` 一次发给实现 Agent。下文是本轮的实施范围和验收标准。

## 总任务

在 Agent Studio 仓库继续开发，从已验收的提交 `9696efa` 接手。请阅读 `AGENTS.md`、[代码开发规范](../开发规范/代码开发规范.md)、原始后端审查附件及[最终验收记录](后端架构重构_最终验收.md)。核对实际 `HEAD` 和用户未提交改动，已经完成的内容以当前代码和测试证据为准。

依次完成下面四项。每项闭环后验证对应入口，再继续下一项。四项完成后集中跑一次全量回归并交付。已有包分层、SDK 隔离、Flyway、模型计价和其他已验收行为继续作为回归基线。MySQL、并行 DAG 和其他产品功能另行排期。

## 统一约定

- 保持 HTTP 路径、方法、已有 JSON 字段、状态码、历史数据读取与默认不限额语义。继续使用 Spring Data JPA 和现有 Flyway 迁移。
- 运行状态和事件保持提交顺序。保留工作区授权、证据版本核对、节点原子认领、请求幂等、创建事务和提交后派发。
- 只用隔离 H2 与合成 Git 工作区验证。保留用户已有数据库、工作区、凭据和未提交文档。需要模型行为时用现有受控模型或桩。
- 保留已有测试和有效断言。新增反例集中在本次行为改动，控制机械改名和全库格式化的范围。
- 按模块组织 Controller、Service、Repository 和 DTO。优先复用现有细粒度服务或窄接口。验收看职责消除和调用点迁移，也要保留接口行为。

## 任务 1 · 兼容流程的审查结算分类

**问题现象**

动态工作流已区分 `USER_REVIEW` 和 `EXECUTION_BLOCKED`。兼容 Bug 路径的审查结算仍可能保存 `STATUS=BLOCKED`、`STOP_CAUSE=null`。隔离实测中，复现成功、只读分析与审查结束、未执行回归的运行返回 `BLOCK_CATEGORY=UNKNOWN`，服务端其实知道原因。

**实现要求**

1. 从 [RunReviewCoordinator](../../backend/src/main/java/dev/workbench/orchestration/RunReviewCoordinator.java) 梳理兼容入口中通过审查等待用户核对、校验缺失、回归未通过和一般完成的分支。让 [ReviewCompletion](../../backend/src/main/java/dev/workbench/store/ReviewCompletion.java) 或现有结算契约携带明确停止原因。
2. 在 [RunStateStore](../../backend/src/main/java/dev/workbench/store/RunStateStore.java) 和 [RunRepository](../../backend/src/main/java/dev/workbench/persistence/repository/RunRepository.java) 的审查更新中一起提交状态、原因、停止码、结果及原有证据。继续使用现有条件更新和提交后通知。
3. 已满足工作流验证条件、等待用户核对的场景使用 `USER_REVIEW`。缺少必要的验证、检查未通过和产出缺失分别使用相应已有停止码，归入 `EXECUTION_BLOCKED`。历史空值和无法识别的旧停止码仍为 `UNKNOWN`，保留已有字段和理由正文。按实际证据分类，避免根据中文理由文本做字符串匹配。

**通过条件**

- 兼容流程的正常待审查、缺验证条件或回归未通过各有至少一个生产结算路径的断言。使用具体案例说明预期的 `STATUS`、`STOP_CAUSE`、`BLOCK_CATEGORY`。
- 新建兼容运行得到明确分类，历史未知仍可读。动态工作流的写入成功、缺少产出及正常完成行为一致。
- 复用 `BugWorkflowIntegrationTest`、`BugValidationBlockingIntegrationTest`、`BlockCategoryTest` 与现有动态流程用例。

## 任务 2 · Git 证据校验移出数据库事务

**问题现象**

[WorkflowExecutionService](../../backend/src/main/java/dev/workbench/task/WorkflowExecutionService.java) 中的 Agent 节点和系统检查认领在 `TransactionTemplate` 内调用 `requireCurrentCheckEvidence`，继而执行本地 Git 状态与差异查询来计算工作区指纹。工作区阻塞会延长运行行锁持有时间。

**实现要求**

1. 把检查证据的读取与外部指纹计算明确分开。可先取得可追溯的预检输入，包含运行与计划版本、依赖检查 ID、外部证据 ID、预期指纹及工作区归属，然后退出数据库事务，在事务外调用 Git 得到当前指纹。
2. 进入短事务后，重新锁定运行并重读计划、节点及直接依赖。核对这次预检对应的证据记录、归属、版本和节点状态仍一致，最后原子认领并保存交接。遇到变化应拒绝使用旧结果或按现有调度边界重新预检。
3. 显式处理「指纹读取后、节点开始前」的工作区变化。沿用工作区协调和执行前授权校验。若现有协调覆盖不了外部编辑，在节点实际发起模型、工具或容器操作前，于事务外按同一证据规格复核，并在短事务内以受控原因结算失效状态。说明能够保证的边界。保持“证据失效时下游不可借此执行”。
4. 同一范围内检查 Git 指纹相关的相邻认领路径，以及运行中检查点保存是否仍在持行锁时调用 Git。记录实际调用链和处理结果。有需要保留的读取边界，应解释原因并给出可验证的锁时长或失败行为。

**通过条件**

- 生产路径的探针或集成测试证明参与认领的 Git 指纹调用发生时没有活动数据库事务。
- 已有证据一致时正常认领。证据记录或工作区在预检后变化时，下游不发起模型、工具或 Docker 调用，原检查证据留存。并发认领仍只产生一次有效尝试。
- 使用现有动态 Bug 证据过期、暂停/取消、重复认领和只读恢复用例，增加必要的可控并发反例。禁止把删除复验当成解耦。

## 任务 3 · 普通与数据集评测以运行完成通知为主

**问题现象**

[EvaluationService](../../backend/src/main/java/dev/workbench/evaluation/EvaluationService.java) 和 [ManagedEvaluationDatasetService](../../backend/src/main/java/dev/workbench/evaluation/ManagedEvaluationDatasetService.java) 接入了完成通知，但未完成时仍以约 200 毫秒为间隔查数据库。

**实现要求**

1. 以 [RunCompletionWaiter](../../backend/src/main/java/dev/workbench/store/RunCompletionWaiter.java) 和已实现的提交后通知为基础。采用「注册等待 → 读取数据库初始状态 → 有界等通知 → 唤醒后确认终态」的模式，覆盖运行早于注册结束和注册后立即结束的竞态。
2. 移除正常等待时固定频率的状态查询。超时可核对一次持久化状态作为兜底。检查可能绕过当前通知逻辑的合法终态路径，确保能及时唤醒。不另起周期性轮询线程。
3. 保留现有超时、取消、停机、中断及状态决策。取消和异常应释放等待资源。若多个消费者等待同一运行，一个消费者的退出不能让其他消费者失去通知。保持不同执行队列互不阻塞。

**通过条件**

- 普通评测和数据集评测都能在运行提交终态后继续，并且长时间运行时没有固定间隔的数据库查询。
- 覆盖结束早于注册、结束接近注册、正常结束、超时、取消或中断。事务回滚不发送完成通知。用可控 Future 或闩锁构造时序。
- 复用 `RunCompletionNotificationIntegrationTest`、`Task5EvaluationConfigIntegrationTest`、`ManagedEvaluationDatasetIntegrationTest`，以及现有队列和取消反例。

## 任务 4 · 迁移 RunRecordService 门面调用方

**问题现象**

[RunRecordService](../../backend/src/main/java/dev/workbench/store/RunRecordService.java) 已拆出细粒度实现，但运行编排、交付投影、评测和观测等核心调用方仍直接注入综合门面。原审查要求核心调用方依赖实际职责。

**实现要求**

1. 列出生产调用方与实际使用的方法，分别归入任务、运行状态与创建、Agent 装配、运行证据、检查点和计数职责。
2. 分组迁移。优先迁移交付投影、事件/指标和评测读侧，再迁移有事务和状态更新的调用。复用 `TaskRecordService`、`RunStateStore`、`RunCreationStore`、`AgentAssemblyRecordService`、`RunEvidenceRecordService`、`RunCheckpointStore` 和 `RunCountStore`。跨层消费优先使用已有窄端口，适合时直接依赖对应服务，避免为每个读取方法增加一层接口。
3. 保持统一创建和状态结算事务，尤其是事件顺序、预算、检查点和恢复。核对改成直接调用后 Spring 代理和事务传播是否仍然生效。
4. 核心生产调用点完成迁移后，把门面收敛到确有必要的兼容入口。确有剩余调用方时逐一列出调用者、保留原因和替换条件。检查编译依赖以免重新引入包循环。

**通过条件**

- 验收提供迁移前后对应关系，核心生产服务不再直接依赖综合门面。兼容保留项有具体消费者和理由。
- 任务、运行、事件、报告和交付 API 字段与权限保持。创建回滚、提交后派发、并发事件游标、运行终态和恢复预算继续通过。
- 复用 `TaskCreationTransactionIntegrationTest`、`EventPersistenceIntegrationTest`、`WorkspaceReadOnlyRecoveryIntegrationTest`、`DeliveryRevocationIntegrationTest` 和 `ArchitectureGuardTest`。保留 ArchUnit 的 5 条规则。
