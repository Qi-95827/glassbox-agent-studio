# Agent Studio 后端架构审查整改交接

> 2026-11-21。审查输入是外部附件 `code_artifact.md`，当前代码基线是提交 `98027a2`。附件用于定位和解释问题。具体实施内容以本交接和当次任务授权为准。

## 1. 审查结论和整改原则

本轮目标是降低后端维护与演进成本。先清理能独立验收的包依赖，再拆职责混杂的服务。数据库迁移、执行策略和费用账本各有独立的数据或行为验收，分别交付。

| 审查意见 | 当前判定 | 落地决定 |
| --- | --- | --- |
| `domain` 和 `framework` 反向依赖 | 已从源码确认。按显式 import 扫描识别 18 对顶层包直接互相引用。这个数字未计入全限定名引用、多跳环和编译后依赖。 | 用可复现的依赖基线和逐批生效的守卫约束。每批清掉一组职责或依赖边。 |
| 类过大、Controller 归属不统一 | 多个核心类同时管理查询、业务规则和事务。跨模块定位确实困难。 | 优先按读写、聚合和状态职责拆分。类和方法的长度用来定位审查点，通过条件以接口、依赖和行为为准。Controller 随业务模块调整。 |
| AgentScope 类型暴露 | 已确认 `framework/model`、`framework/tool` 和会话服务中有 SDK 引用。 | 保持现有执行能力，逐个收口直接依赖。在确有独立消费者或替换需求时定义窄接口。 |
| Flyway | 可以单独改善版本化迁移。原稿的 `baseline-on-migrate=true` 和 `baseline-version=1` 会让已有非空库跳过 V1。旧库如未达到 V1 结构，缺列、缺约束或回填缺失仍会存在。 | 先设计旧库升级路径，再决定切换。仓库的 Maven 入口为根目录 `pom.xml`，资源路径为 `backend/src/main/resources`。 [Flyway Baseline 文档](https://documentation.red-gate.com/flyway/reference/commands/baseline) |
| 线程池、状态和混合模型费用 | 涉及排队、取消、账本和用户可见语义。现有费用硬预算有单模型约束，运行仍为顺序执行。 | 分开验收。架构整改阶段保留现有业务语义。 |

原稿第一阶段同时要求架构守卫预期失败和 Maven 全绿，交付口径冲突。已有违规先登记成可比对的基线。第一批只启用在本批收口后能通过的守卫。存量违规多的规则可以冻结，之后仅接受减少。 [ArchUnit 渐进治理指南](https://www.archunit.org/userguide/html/000_Index.html#_freezing_arch_rules)

## 2. 各批次共用的验收约束

- 保持 HTTP 方法、路径、请求及响应字段、状态码兼容。现有扁平任务 JSON 继续可反序列化。节点状态、历史读取、审批与报告证据保持既有语义。
- 保持任务、运行、计划、授权及事件的创建事务，派发只能在提交后发生。核对并发认领、条件更新、短引用固定版本、重复确认、事件提交顺序、未知副作用和恢复租约。
- 迁移可先引入直接调用点适配，逐批移除旧实现。新增接口须有清晰的依赖反转价值，新增类须有单一职责。业务验证需要和锁定、更新处于同一正确事务边界。
- 外部调用应与数据库事务分清边界。调整 Git、模型或文件操作的位置时，需要核对执行先后、失败收口、幂等和取消传播，不能直接移动一行调用就算完成。
- 保留已有测试及断言。按批次改完后集中回归一次，并列出实际执行与跳过的用例。测试使用隔离库与临时工作区。原 H2、已有 Git 工作区、凭据和其他未提交改动应保留。
- 每批交付说明列出旧位置、新职责、依赖变化、兼容证据、测试结果和剩余问题。沿用现有 Spring Data JPA、Hibernate 和 Git 工作约定。 [代码开发规范](../开发规范/代码开发规范.md) · [关键流程验收约定](../开发规范/关键流程开发与验收约定.md)

## 3. 建议的实施顺序

| 批次 | 目标与改动范围 | 结项标准 |
| --- | --- | --- |
| **1 · 基线与领域包边界** | 记录生产包依赖。将 `EntryRouteService`、`EntryPolicyService` 迁入 `planning`，同步调用和测试位置，保持其事务和持久化映射。增加领域包不得引用 JPA、Spring Data 和 `persistence` 的守卫。 | 四类入口路由、策略持久化、任务创建回滚和 API 都保持行为。相关依赖规则在正常 Maven 测试中启用。剩余依赖作为基线记录。 |
| **2 · 事件和执行视图** | 先迁出事件 Controller 与查询聚合，再迁出 `ExecutionViewService`。以图投影、节点证据、可用操作为候选拆分点。Controller 随对应业务模块迁移。 | 响应字段、游标和旧事件兼容。复核跨运行隔离、并发提交顺序、分页去重、断线回补和节点详情。动作权限由服务端原规则判定。启动期事件回填保持既有执行顺序。 |
| **3 · 运行记录与核心服务** | 从 `RunRecordService` 的任务读取和证据读取开始，每次拆一项职责。后续分别处理私有组件、运行命令、工作区 Git 与文件、候选生成与确认，再按职责调整 Repository。Controller 和 DTO 只随各自用例调整。 | 读侧字段不变。写侧逐项覆盖原子认领、事件顺序、回滚、候选幂等、锁与事务边界。私有版本绑定、节点授权、未知写入、审批及交付不退化。扁平 JSON 用既有入口提交成功。 |
| **4 · AgentScope 适配边界** | 在原装配、策略和工具契约基础上，迁移 SDK 面向的模型、Toolkit 和会话适配。优先从模型和工具各选一个实际调用路径。依赖规则在迁移完成后扩到相应范围。 | 执行证据、模型用量、限流重试、工具拒绝、取消和会话读回行为保持。最终只有配置装配和具体适配层依赖 SDK。 |

扩展守卫时先解决确定的反向边，再按需检查跨模块循环。使用全仓规则前，以真实分析结果确认统计口径。验收记录应区分扫描到的直接双向边和完整依赖图中的环。

## 4. 独立决策与实施项

### A · Flyway 与旧 H2 升级

- 先明确支持的旧库版本和迁移起点，说明新库初始化、旧库升级和错误结构拒绝三条路径。校验旧库实际达到哪个 schema 版本后再选匹配的迁移基线。
- 建表、约束、索引和数据回填都要核对。注意旧预算表迁移、事件 `run_seq` 回填、历史计划及 AgentScope 会话。新增迁移与现有启动回填应有明确顺序和唯一职责。
- 验收包括空库启动、低于基线的旧结构副本、已经达到基线的副本、同一副本连续启动及备份恢复。对比实际连接地址、行数、核心历史读回与迁移标记。源库保持隔离。
- 该项以 H2 为范围。Docker MySQL 驱动、DDL 兼容和历史数据搬迁按既有待办独立实施。 [扩展方向与 MySQL 待办](../迭代计划/1.1及以后_扩展方向.md)

### B · 异步执行与停机

- 用命名执行器明确区分运行、规划和评测职责，起步保留原顺序和必要的执行隔离。评测的等待方与被调度的运行不能争用同一条阻塞队列。
- 替换等待方式前分别核对候选生成取消、工作区准备租约和评测等待。每种等待的结束、超时和失败原因需要与现有状态一致。
- 验收覆盖候选排队取消、晚到结果不能覆盖状态、重复确认只派发一次、评测可等待完成、队列拒绝、应用停机和中断状态。并行 DAG 另行设计。

### C · 等待审查与执行阻塞

保留现有 `BLOCKED` 和历史映射。先对齐现有停止原因、等待审查以及可用操作的判定。若产品需要更直观的区分，优先兼容新增分类字段。验收正常等待人工核对、缺少输入、检查失败、产物缺失和未知写入能被区分，同时旧前端仍可加载和操作。

### D · 混合模型费用硬预算

这是费用功能扩展。保留预算可空的默认行为。设计通过后按每次调用的实际模型和已固定的价格版本预留与结算，汇总到运行总上限。覆盖零费用模型、一种及多种模型、调用前预算不足、用量未知、实际超支、重试与恢复继承。实际超支应留到账本，缺价或预算不足应在发起调用前处理。真实费用核验另行登记。
