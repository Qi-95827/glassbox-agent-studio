## 2. 先修已发现的行为缺口

### A · Flyway 升级

V1 在表已存在时跳过建表，随后添加依赖新列的外键。V2 才添加 `plan_version_id` 与 `source_checkpoint_id`，因此老结构可能在 V1 阶段失败。双启动测试仍含 `--spring.sql.init.mode=always`，需要补一个与生产配置一致的路径。 [V1](../../backend/src/main/resources/db/migration/V1__baseline.sql#L1031) · [V2](../../backend/src/main/resources/db/migration/V2__legacy_upgrade.sql#L49)

- 声明支持的旧库起点，在添加外键和索引之前补齐依赖列。明确处理空库、旧结构、当前历史结构和初始化失败后的重试。
- 迁移测试直接走实际 Flyway 与生产初始化选项，明确使用 `spring.sql.init.mode=never`。旧脚本仅用于准备必要的历史测试结构。
- 至少包含四个对照。空库启动。旧 `plan_nodes` 缺 `plan_version_id` 的夹具。当前 H2 历史副本。既有 Flyway 安装的升级与重复启动。核对 Flyway 历史、数据库连接地址、外键、索引、行数与关键历史回读。
- 兼顾已经应用 V1、V2 的数据库的校验和。已发布迁移若需兼容处理，明确具体路径和验证结果。备份和失败回退只操作隔离副本。MySQL 适配仍由既有待办安排。

### B · 异步收口

规划候选持久化为 `GENERATING` 后提交线程池，拒绝时缺少收口和内存清理。管理版评测也需核对提交拒绝和持久化状态。 `AsyncDelay.await(100)` 仍阻塞等待线程，外围循环会继续查询数据库，`join()` 也不提供旧 `Thread.sleep` 的可中断语义。 [规划提交](../../backend/src/main/java/dev/workbench/planning/PlanCandidateService.java#L202) · [评测提交](../../backend/src/main/java/dev/workbench/evaluation/ManagedEvaluationDatasetService.java#L306) · [AsyncDelay](../../backend/src/main/java/dev/workbench/framework/concurrent/AsyncDelay.java)

- 加入确定性的拒绝或饱和用例。候选、运行、评测持久化状态须落在可理解的结果。保留候选重试幂等，释放 Future、队列和租约相关资源。明确新规划提交失败时同组旧候选的处理结果。
- 规划准备等待和两类评测等待改为可超时、可取消的完成通知或有界等待契约。分别验证队列中的任务取消、晚到响应、重复确认、评测能得到运行终态、停机时待办结果与中断传播。
- 保持跨运行队列、运行内顺序调度、提交后派发及各次尝试证据。不把并行写入并入本轮。

### C · 混合费用预算

不同价格版本可以发布不同币种，运行账本目前把各模型的微单位直接相加。同时，确认页仍提示「混合模型带硬预算会被拒绝」，费用接口的预留列表也未展示单次实际价格版本。 [计价与估算](../../backend/src/main/java/dev/workbench/task/CostService.java#L112) · [确认页](../../frontend/user-workbench/src/features/workflows/PlanCandidateDialog.jsx#L302)

- 硬预算启用时，在候选确认阶段核对实际模型集合、必需价格和同一计价币种。保留派发前拒绝的保护。不同币种或缺价给出明确原因。
- 明确价格发布对运行中的任务有何影响，记录每个实际模型绑定的价格版本，保护原有单模型固定价格和恢复继承语义。保留旧账本和旧费用字段的可读性。
- 用混合模型真实执行路径的桩或本地模型测试校验确认、两种模型预留和结算、预算拒绝不派发、结算过额先落账、未知用量保留预留、子运行继承余额。更新前端文字和单次价格证据，预算留空仍表示无费用上限。

## 3. 继续完成原审查的结构拆分

每一行是一个可独立交付的功能范围。多项内部修改可以同批完成，批末一次集中回归。行数用于定位问题，结项看职责、依赖、API 和行为证据。

| 次序 | 处理范围 | 验收重点 |
| --- | --- | --- |
| 1 | `store/RunRecordService` 拆开任务读取归档、运行状态、Agent 装配和调用证据。兼容门面逐步瘦身，接入方移向实际职责。 | 任务创建和回滚、运行状态原子更新、事件顺序、检查点、历史查询、装配证据。 |
| 2 | `delivery/ExecutionViewService` 拆出图投影、节点证据和操作判定。收口 `WorkbenchController` 任务与运行的职责。 | 执行图、列表、节点详情、操作和报告的 JSON 与权限。编制具体 HTTP 契约对照。 |
| 3 | `PrivateComponentService` 按私有 Agent、Skill、工具配置和版本解析拆开。 `AgentScopeExecutor` 收紧模型适配的类型契约。 | 私有版本、候选短引用、归档撤权、真实装配与调用能力、跨账号隔离。 |
| 4 | `RunService` 拆派发与运行命令， `PlanCandidateService` 拆候选生成、仓库准备与确认物化职责。 | 提交后派发、确认幂等、候选取消与过期、工作区租约、恢复、停止、同事务创建和失败重试。 |
| 5 | `WorkspaceService` 拆文件访问与 Git 交付， `WorkflowExecutionRepository`、`InvocationRepository` 收敛组装和校验。 | 文件授权、证据版本与外部结果不确定性保持语义。保留条件更新、行锁、版本校验与原子结算，避免 Repository 瘦身拆掉同一事务的必要校验。 |
| 6 | `BLOCKED` 补一级分类，默认兼容已有 `status` 和停止原因。ArchUnit 规则增加项目自有 Repository 依赖检测。 | 正常待审查与缺失输入、检查失败、产出缺失和未知写入明确区分。旧用户端和历史运行仍可读。 |
