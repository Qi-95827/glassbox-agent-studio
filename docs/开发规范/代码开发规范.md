# 代码开发规范

> 适用范围：本项目的后端、前端、配置、测试和设计文档。本文是后续开发时应遵循的项目约定；现有代码不一定已全部达到，发现差距应结合当前任务逐步改进，不把规范当成已完成的功能。

## 1. 先理解、再设计、再实现

1. 开发前阅读相关概要设计、迭代计划、模块代码和开发记录，明确本次目标、范围、依赖及已知限制。
2. 新增或明显修改核心功能时，先在概要设计或相应的模块设计中明确职责、输入输出、领域类型、状态变化、权限、安全边界、异常与验收，再实现代码。小范围修复可以直接修改，但若改变了已有设计或约定，应同步更新文档。
3. Agent、工具、记忆、Checkpoint、预算、协作和可观测等框架能力，先确定模块边界及其与上下游的关系，不靠大量空接口假装功能已经完成。
4. 涉及真实模型、外部系统或有副作用的操作，应说明授权、数据去向、失败和结果未知时如何处理；模拟功能必须明确标识。
5. 代码、设计文档和实际行为不一致时，以实际代码和已验证结果为事实，及时修订或记录差异。

## 2. 中文注释与文档

1. 使用规范、准确的中文注释。类、接口、枚举、重要公开方法和复杂数据结构，应根据阅读需要说明职责、用途和边界；重要字段及枚举值说明含义，必要时注明单位、取值或为空的意义。
2. 对并发、状态迁移、超时、重试、幂等、取消、预算扣减、权限、外部副作用和恢复等不直观逻辑，重点解释**为什么这样处理、依赖什么前提、有哪些限制**。
3. 公开方法在参数、返回值、异常含义不明显时，使用 JavaDoc 的 `@param`、`@return`、`@throws` 等说明；简单方法不强制添加重复签名的模板注释。
4. 注释要与实现同步，发现过期、错误或误导性注释应修正。不要逐行翻译代码、堆砌无意义注释，也不要声称未验证的能力已经实现。
5. 面向用户的提示、日志和文档应清晰说明成功、失败、未验证及未知状态；模型的推断不能写成工具已经执行的事实。
6. 示例和文档不得包含真实密钥、访问令牌、用户隐私或未经授权的代码内容。

## 3. 类型、枚举与数据契约

1. 按业务含义选择类型：固定且受控的状态、事件、模式、阶段等优先考虑枚举；标识、时间、数量、金额、时长和集合使用能表达语义的类型，并明确单位、范围及精度。
2. 不要把固定枚举值、布尔状态、数字或时间无差别地写成 `String`，也不要在核心业务流程中长期用 `Map<String, Object>` 隐式传递已知结构。输入、领域和输出使用明确的数据对象，在边界做校验和转换。
3. 开放文本如用户目标、模型回答和错误说明，可以使用字符串；外部系统可扩展的值不应为了使用枚举而被错误地封闭。是否使用枚举，以业务边界是否稳定、是否由本系统控制为依据。
4. 枚举持久化和接口编码应稳定且显式，避免依赖顺序值 `ordinal()`；新增、删除或改名时考虑历史数据、接口调用方、前端和兼容迁移。未知值应明确处理，不得静默当作成功或默认值。
5. 区分零值、空值、未知和不适用。例如没有收到模型用量时不能记录为 0 Token；时间、费用和资源数据必须说明统计口径和归属范围。
6. 涉及结构化交接、事件、工具结果和检查点的字段，在设计中记录来源、类型、必填性、版本及兼容规则；保留可追溯的证据引用。

## 4. 模块与代码结构

1. 按功能职责组织目录和代码，让人能找到任务、Agent、编排、模型、工具、记忆、控制、检查点和可观测等模块；目录预留与已实现能力要区分。
2. 类和方法保持明确职责；输入校验、业务规则、外部适配、持久化及展示尽量分开。避免把编排、安全、数据库、模型请求和页面行为全部堆进一个类。
3. 模块通过清晰的数据契约协作；只对确有调用场景或稳定边界的能力定义接口，避免过度抽象和无实际行为的占位实现。
4. 命名清楚表达业务意义，统一语言和风格；避免难以理解的缩写、魔法数字、重复代码和高度压缩的一行式实现。外部接口字段名需遵守兼容约束。
5. 对所有依赖和组件写清职责；真实依赖版本、许可证和能力在引入时核验。不要仅因为组件或框架声称支持某能力，就认为本项目已经完成。

### Java 排版约定

1. 使用 Google Java Format 的默认 Java 风格：两个空格缩进，不使用制表符缩进；统一大括号、换行、运算符和逗号空格。
2. 字段按职责适当分组；构造方法、普通方法、内部类型等成员之间保留一个空行，不用多重空行。方法内部只在逻辑段落之间保留必要空行。
3. 优先每个主要职责一个类／文件；包和导入清晰，不用格式美化掩盖过大的类。自动格式化覆盖不了的注释准确性、命名和职责拆分仍需人工检查。
4. 本项目当前使用 `google-java-format 1.28.0`；修改 Java 后对相关文件格式化，在整轮回归中检查构建。用户要求按迭代集中测试，必要的失败修复可复测。

## 5. Agent 执行、安全与恢复

1. 模型输出是不确定的，工具使用、权限和预算由系统控制；不可用提示词或 Skill 替代权限检查，也不能将外部内容当作系统指令。
2. 明确任务、运行、Agent、模型、工具和事件之间的关联；结构化交接应保留目标、约束、状态、来源和证据，不能仅依赖自然语言摘要。
3. 为相应能力设计调用次数、轮次、时间及可获得的 Token／费用等限制；实现取消传播、超时和合理的错误分类。失败调用与重试也要计入适用的消耗。
4. 检查点保存的是有范围和版本的内部状态；创建、读取、校验和恢复必须与已支持的安全节点一致。恢复不应使已记录消耗倒退，也不能把 Git 提交、代码工作区和内部状态当作同一回事。
5. 外部操作超时或进程中断时，结果可能未知；依据具体能力查询状态、使用幂等保护或交人工处理，不得盲目重复或宣称恰好一次。
6. 最小权限、凭据保护、日志脱敏和访问隔离与能力一同设计、实现和验证；当前个人本地版不应被误称为已完成多租户安全隔离。

## 6. 测试、检查与交付

1. 每完成一个有意义的功能或修改，执行与风险匹配的检查：正常流程、关键边界和失败路径；必要时覆盖取消、超限、并发、宕机恢复、旧数据兼容、权限与外部调用错误。
2. 测试应验证实际行为和用户关心的结果，而非仅复述代码实现。外部模型适配优先使用本地受控模拟进行自动化检查；真实服务验证时说明是否产生费用，不暴露密钥。
3. 前端改动检查功能联动、必要的响应式和可访问性；设计中的指标和状态必须来自实际数据。用户已记录的视觉优化要求应在相应专项中复查。
4. 构建、测试或环境检查失败时先定位问题，说明影响并修复；确实无法验证的内容记录原因和边界，不能声称已通过。
5. 更新开发记录：说明改了什么、为什么、执行了哪些检查、结果及已知限制；涉及设计变更时同步更新设计。不得把“计划”“占位”或“模拟通过”写成真实功能已完成。
6. 使用 Git 保存代码历史；提交前检查变更范围和敏感信息，遵守项目分支策略。产品版本、提交和标签含义分别记录，不因代码存在就自动宣称发布。

## 7. 本项目目前的特别约定

- 目前优先实现个人使用的 0.1 Agent 基础框架；多人共同操作任务不是第一版目标，多租户共享部署按迭代计划推进。
- `config/deepseek-api-key.txt` 为用户的本地密钥文件，已加入 Git 忽略；禁止打印、复制到文档或加入版本控制。
- 前端视觉有用户明确提供的参考图和待办，见 [开发记录](../开发记录/开发记录.md)；在用户要求的时机再做专项优化。
- 类型与状态设计的当前范围见 [0.1 领域类型与状态设计](../概要设计/0.1_领域类型与状态设计.md)。后续涉及新领域类型，先更新对应设计，再实现。
