# 任务 2 等待补充信息、任务版本与安全继续设计

> 承接[产品开发与验收交接](../交接/动态Agent重构后_产品开发与验收交接.md)任务 2 与任务 1 的阻塞／操作接口。状态为已实现并验收（2026-11-19），交付证据见[任务 2 交付记录](../交接/任务2_等待补充信息与安全继续_交付记录_2026-11-19.md)。

## 1. 范围与目标

用户在流程图上完成「缺信息 → 阻塞 → 补充 → 重新校验 → 按安全边界继续」：

- 首个复现检查因缺少可执行测试而阻塞时，运行保存一条**待补充事项**（稳定原因、关联节点、提问与任务版本），流程图显示问题与可回答的表单。
- 用户提交补充（本期为一个新的 `tests/test_*.py` 测试文件）。服务端在同一事务内校验：请求归属与状态、提交目标任务版本、任务授权与已批准计划一致、运行仍处于**零调用的安全边界**、目标文件此前不存在。
- 校验通过后：文件写入任务工作区（未跟踪）、任务版本 +1、失败检查节点与未启动下游回到待执行、运行回到排队并重新派发。原运行链路保持不变，历史检查记录与事件全部保留。
- 校验失败：运行与请求状态不变，记录 `SUPPLEMENT_REJECTED` 事件并返回明确原因；重复或过期提交不会再次调度。

不改变：已批准计划的原始记录、既有恢复（检查点子运行）语义、流程图既有阻塞与操作口径。

## 2. 领域状态

### 2.1 补充请求

```
（无） --复现检查 NEEDS_INFO 结算--> OPEN --用户提交且全部校验通过--> APPLIED
```

- `OPEN` 请求同一运行最多一条；阻塞再次发生时若已有 `OPEN` 请求则不重复创建。
- `APPLIED` 为终态：再次提交同请求被拒绝（幂等）。校验失败的提交不改变请求状态，仍为 `OPEN`，等待正确提交。
- 本期唯一种类 `TEST_FILE`：补充一个模拟 Bug 的 unittest 入口文件。

### 2.2 任务版本

- `tasks.version` 整数，创建时为 1。
- 接受一次补充 +1（旧值记录在请求行）。提交必须携带期望版本；不匹配即拒绝，防止过期表单覆盖新状态。
- 目标、授权范围等任务字段当前没有编辑入口；若外部变化导致授权摘要不再匹配已批准计划，补充被拒绝（“不得复用无效审批”）。

### 2.3 运行状态链

```
BLOCKED(CHECK_FAILED，零调用) --接受补充（同一事务）--> PENDING --重新派发--> RUNNING
```

继续条件（全部满足才允许）：

1. 运行 `BLOCKED` 且 `stop_cause=CHECK_FAILED`。
2. 失败节点是 `bug-reproduction` 系统检查，且最新检查记录为 `BLOCKED`（对应 NEEDS_INFO）。
3. 该运行没有任何 Agent 实例、模型或工具调用（安全边界＝首个节点之前；容器检查不产生调用）。
4. 已批准计划仍匹配当前任务授权（`requireTaskAuthorization`）。
5. 该运行没有已派发的恢复子运行。

## 3. 数据与迁移

```sql
ALTER TABLE tasks ADD COLUMN IF NOT EXISTS version INT DEFAULT 1 NOT NULL;

CREATE TABLE IF NOT EXISTS run_supplements (
  id VARCHAR(36) PRIMARY KEY,
  run_id VARCHAR(36) NOT NULL,
  node_id VARCHAR(36) NOT NULL,
  reason_code VARCHAR(50) NOT NULL,
  question VARCHAR(500) NOT NULL,
  kind VARCHAR(30) NOT NULL CHECK(kind IN ('TEST_FILE')),
  status VARCHAR(30) NOT NULL CHECK(status IN ('OPEN','APPLIED')),
  answer_path VARCHAR(200),
  answer_sha256 VARCHAR(64),
  task_version INT NOT NULL,
  created_at VARCHAR(40) NOT NULL,
  decided_at VARCHAR(40)
);

CREATE TABLE IF NOT EXISTS workspace_declared_files (
  workspace_id VARCHAR(36) NOT NULL,
  path VARCHAR(200) NOT NULL,
  sha256 VARCHAR(64) NOT NULL,
  source VARCHAR(30) NOT NULL,
  created_at VARCHAR(40) NOT NULL,
  PRIMARY KEY(workspace_id,path)
);
```

- **指纹规则**：`verificationFingerprint` 允许已声明补充文件以未跟踪状态存在，但按“路径 + 当前内容 SHA-256”加入指纹；内容变化或文件删除都会改变/拒绝指纹，使旧检查证据失效。其他任何未跟踪文件仍直接拒绝，审批签名继续拒绝所有未跟踪文件。
- `SystemCheckResult` 新增可空 `reasonCode`：`REPRODUCTION_MISSING_INFO`（复现缺测试）、`REGRESSION_MISSING_INFO`（回归缺测试）。仅前者生成补充请求；无法绑定工作区版本（未声明未跟踪文件等）记 `STALE`，不生成补充请求。
- 事件新增：`SUPPLEMENT_REQUESTED`、`SUPPLEMENT_SUBMITTED`（并入 APPLIED 事件前不单独记录，避免噪音，最终采用 REQUESTED/APPLIED/REJECTED/CONTINUED 四类）、`SUPPLEMENT_APPLIED`、`SUPPLEMENT_REJECTED`、`CONTINUED_AFTER_SUPPLEMENT`。

## 4. 接口

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| `POST` | `/api/runs/{id}/supplements/{requestId}` | 请求体 `{expectedTaskVersion, path, content}`。成功返回 `{accepted, taskVersion, runStatus}`；失败 400 + `{message}`，运行不变。 |
| `GET` | `/api/runs/{id}/execution-view` | 顶层新增 `taskVersion`；存在补充请求时新增 `supplement` 对象；`OPEN` 时 `availableActions` 含 `SUBMIT_SUPPLEMENT`。 |

`supplement`：`{id,status,kind,reasonCode,question,nodeId,nodeLabel,answerPath,answerSha256,taskVersion,createdAt,decidedAt}`。

## 5. 服务端流程（`TaskSupplementService.apply`）

单事务（持有运行行锁）：

1. 锁运行行，校验状态 `BLOCKED`、`stop_cause=CHECK_FAILED`。
2. 读取该运行唯一的 `OPEN` 请求，`requestId` 必须匹配。
3. 锁任务行，`expectedTaskVersion == tasks.version`。
4. 校验路径 `tests/test_*.py`、内容 1–20000 字符、工作区内该文件不存在（以原子 `CREATE_NEW` 判定，并发同名提交只有一个成功）。
5. 读取计划与任务，`plan.requireTaskAuthorization(task)`。
6. 校验零 Agent／模型／工具调用、失败节点与最新检查记录、无恢复子运行。
7. 写入测试文件（未跟踪）并登记为工作区声明文件（路径 + SHA-256）；后续数据库更新失败时尽力删除该文件与声明。后续复现、回归和证据复核通过“路径 + 内容摘要”把该文件纳入工作区指纹，其他未跟踪文件仍被拒绝。
8. 更新：请求 `APPLIED`（含路径、SHA-256、旧任务版本）、`tasks.version+1`、检查节点 `FAILED→PENDING`、`SKIPPED→PENDING`、运行 `BLOCKED→PENDING`（清 reason/stop_cause）。
9. 事件：`SUPPLEMENT_APPLIED`（带计划／节点引用）、`CONTINUED_AFTER_SUPPLEMENT`。

事务提交后由 `RunService.dispatchContinuation` 重新排队（与首次派发同一执行队列语义）。任一校验失败：整个事务回滚，另起事务写 `SUPPLEMENT_REJECTED` 事件并抛出带原因的异常。

## 6. 前端

- 流程图面板在阻塞区下方显示“等待补充信息”卡片：问题、关联节点、当前任务版本、状态（待补充／已补充）。`OPEN` 时提供路径与内容表单及提交按钮；提交后按轮询自然刷新。
- 已补充（`APPLIED`）显示补充文件路径与时间；图上复现检查节点重新进入待执行并随后运行。

## 7. 验收

| 项 | 证据 |
| --- | --- |
| 未补充前零下游写入 | 阻塞运行无 Agent／模型／工具记录；下游全部未执行 |
| 缺信息阻塞显示问题 | 执行视图含 `supplement`，页面显示提问与表单 |
| 过期／重复提交不调度 | 版本不匹配、重复提交均 400，运行保持 `BLOCKED`，仅新增拒绝事件 |
| 授权变化不复用审批 | 修改任务授权后提交被拒 |
| 补充后安全继续 | 同一运行复现检查第 2 次尝试通过，下游节点随后执行，任务版本 +1，事件完整 |
| 补充文件与证据 | 声明文件按路径和内容进入复现、回归与证据指纹；内容变化或删除使旧证据失效，其他未跟踪文件仍被拒绝 |
| 页面与记录一致 | 流程图节点状态、检查尝试、事件与 API／数据库一致 |

模拟回归使用 Docker 容器与 mock 模型；真实验收允许 1–3 次 deepseek-flash 合成任务运行。
