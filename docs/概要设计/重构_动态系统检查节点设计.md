# 动态工作流系统检查节点设计

> 实施日期：2026-11-18。对应重构验收 A04、A10—A12、A20、A25，以及交接文档任务 1。本文描述首个可执行的系统检查节点、持久化与迁移、调度和失败边界；模拟 Bug 检测的执行器在任务 2 接入同一契约。

## 1. 目标与边界

动态计划此前只允许 Agent 节点。本设计增加第二类真实执行的节点：**系统检查节点**。检查节点由受信注册的确定性执行器处理，不创建 Agent 实例、不调用模型，也不申请工具；其结果、输入版本和阻塞原因按本次计划保存，并可被下游节点引用。

首期范围：

- 节点类型固定为受信代码注册的标识加版本；未知标识或版本在保存、确认和认领阶段显式拒绝。
- 首个执行器为 `authorized-read-evidence@1`（授权读取证据检查）：核对直接前置节点确有已结算的授权文件读取或搜索调用，否则判定失败并阻塞必需下游。
- 一个检查失败或无法判定时，运行终态为 `BLOCKED`，停止原因为 `CHECK_FAILED`；未启动节点标记 `SKIPPED`，不再调度。
- 检查节点不参与基于 Agent 定义的恢复边界；现有纯文本 Agent 检查点语义不变。

不在本次范围：节点内用户审批等待、并行检查、模型自行选择检查项、外部命令或容器执行、检查结果自动改写计划。

## 2. 领域类型与标识

| 类型 | 含义 |
| --- | --- |
| `PlanNodeKind` | `AGENT`、`SYSTEM_CHECK`。历史节点没有该列时按 `AGENT` 读取。 |
| `SystemCheckRef` | 检查标识与正整数版本，例如 `authorized-read-evidence@1`。 |
| `SystemCheckStatus` | `RUNNING`、`PASSED`、`FAILED`、`BLOCKED`、`INTERRUPTED`。仅 `PASSED` 视为检查通过；`BLOCKED` 表示缺少判定条件，`FAILED` 表示检查条件不成立。 |
| `SystemCheckExecutor` | 受信执行器：声明引用，接收本次运行的只读输入，返回状态、摘要和结构化证据文本。执行器不得访问未在输入中给出的来源。 |
| `SystemCheckRegistry` | 启动时校验唯一引用和版本合法；解析未注册的标识或版本时抛出明确异常。 |
| `WorkflowCheck` | 一次检查尝试的持久化视图：检查标识、版本、状态、摘要、输入摘要、起止时间和输入引用。 |

检查节点在 `plan_nodes` 中保存 `node_kind`、`check_id`、`check_version`；其 `definition_*`、`permission_role`、`workspace_read`、`workspace_write` 均为空或假，避免伪造 Agent 定义和权限。

## 3. 输入、输出与交接

1. 认领检查节点时，在同一事务内重新锁定运行、复核计划摘要与依赖，读取直接前置节点已结算的结果和工具证据。
2. 检查输入写入 `workflow_check_inputs`，记录来源节点、来源运行、来源尝试或来源检查、结果摘要（SHA-256）。结果内容本身仍以 `agent_invocations`、`workflow_checks` 为唯一权威来源，不复制正文。
3. 检查通行后写 `workflow_checks.summary` 作为可交接结果。Agent 下游消费检查结果时，在 `workflow_handoff_checks` 保存接收收据；检查结果文本进入下游输入，来源类型为 `SYSTEM_CHECK`。
4. 检查消费 Agent 前置时使用同一张输入表；它不创建 `workflow_attempts`、`workflow_handoffs`，因此不会出现在 Agent 尝试或模型调用统计中。

## 4. 执行与事务边界

```text
就绪检查节点
  → 事务 A：复核运行/计划/依赖，条件更新节点为 RUNNING，插入 workflow_checks(RUNNING) 和输入引用
  → 事务外：受信执行器运行确定性检查（不进行模型或外部写入）
  → 事务 B：结算检查记录与节点状态
       ├ 通过：继续下一就绪节点；全部结算后与运行终态一起提交
       └ 失败/阻塞：节点 FAILED，其余未启动节点 SKIPPED，运行 BLOCKED 并记录原因与事件
```

事务 A、B 与 Agent 路径共用运行行锁和“有在途节点时拒绝认领”的约束，因此同一节点不会被重复调度，检查也不会与 Agent 并行越过顺序边界。执行器不进行外部副作用，不需要长事务；事务 B 失败时检查记录保持 `RUNNING` 且节点仍为 `RUNNING`，运行按现有停止路径处理，不伪造通过。

检查失败不是运行异常：不写 `agent_invocations`，不扣模型或工具预算；已发生的既有消耗保留。

## 5. 关卡语义

- `authorized-read-evidence@1` 至少要求一条前置 Agent 节点的 `WORKSPACE_READ` 或 `WORKSPACE_SEARCH` 已结算调用；没有证据即 `FAILED`。授权范围变化、前置未结算或结果为空由认领复核拦截。
- 检查仅允许出现在工作区范围内模板；纯文本模板使用该检查会在保存计划时被拒绝。
- 检查失败时所有依赖它的节点不会启动；用户可在运行详情查看节点状态、检查记录和阻塞原因。
- 未知节点类型、未知检查标识或版本在读取、确认、认领时抛出可定位错误，不创建实例或检查记录。

## 6. 保存、摘要与兼容

- `plan_nodes.node_kind` 默认 `AGENT`，历史记录按 Agent 含义读取；`plan_node_shape` 约束升级为兼容两类节点。
- 图摘要算法只在图包含系统检查节点时切换到 `workflow-graph-v5`。仅含 Agent 节点的历史计划继续使用原算法，保存的摘要仍可通过复核。
- 模板 `workspace-analysis` 升级到 v2：`inspect → evidence-check → summarize`，`summarize` 同时依赖 `inspect` 与检查节点。历史 v1 运行保留原计划与摘要。
- 含系统检查节点的计划不生成动态恢复边界（`workflow_checkpoints`），`checkpoints` 查询为空；Agent-only 纯文本恢复保持原规则。
- 新增 schema 只使用 `IF NOT EXISTS` 追加，重复启动不改变既有记录。

## 7. 可观测与 API

- 运行详情新增 `workflowChecks`：每次检查尝试的标识、节点、状态、摘要、输入摘要、起止时间和输入来源。
- 事件新增 `CHECK_STARTED`、`CHECK_FINISHED`；阻塞时沿用 `BLOCKED` 事件。
- `planNodes` 增加节点类型和检查引用；检查节点不显示角色、Agent 实例或模型调用。
- 图表、报告和评测的展示与统计在任务 5 统一补齐；本任务先保证 API 可核对。

## 8. 验收与测试

1. 正常路径：工作区只读模板实际运行时，`inspect` 产生真实读取调用；检查通过并保存输入引用；`summarize` 输入含检查结果与 Agent 交接；模型调用数等于 Agent 节点数。
2. 失败路径：前置节点没有读取/搜索证据时检查失败，运行 `BLOCKED`/`CHECK_FAILED`，下游 `SKIPPED`，API 可见原因，且不新增 Agent 或模型调用。
3. 门禁：计划未确认时零认领；重复认领检查节点被拒绝；检查插入失败的注入下节点保持 `PENDING`、无检查记录。
4. 未知类型：未注册检查引用在保存计划与认领时拒绝；数据库中不受支持的节点类型读取时报错而不伪造实例。
5. 兼容：旧 Agent-only 计划摘要与历史节点仍可读取；重复启动迁移不重复写入。
