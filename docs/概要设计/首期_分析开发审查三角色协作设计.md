# 分析、开发、审查三角色协作设计

## 目标与执行边界

在现有两角色基础上，为用户明确授权单文件写入的任务增加独立开发 Agent：**分析（只读）→ 开发（在授权文件范围内读写）→ 回归（仅模拟 Bug 且具备条件时）→ 审查（无工具）**。普通只读任务仍为分析 → 审查。角色在同次运行中使用各自独立的 AgentScope 上下文，框架继续承担模型与工具执行；项目协调器控制固定顺序、权限、预算、交接及验证。

## 计划、权限和交接

创建运行时根据服务端确认的写入授权生成两个或三个固定计划节点；开发依赖分析，审查在写入任务中依赖开发。分析只注册模拟检查和授权读取，开发只注册授权读取及写入，审查不注册工具；角色能力与任务授权取交集，模型不能修改授权。用户授权不代表一定发生写入，写入仍需读取当前哈希并经工作区服务校验。

分析向开发提交包含目标、约束、验收要求、分析结论和工具事件引用的结构化交接，实际序列化内容用于开发 Agent 输入；开发结果和实际工具事件再交给审查，输入保留分析与开发结论并区分真实回归记录。模型推断不能当作代码或测试事实。每个 Agent 记录独立实例及模型／工具调用，三个角色共享总轮次、工具、已报告 Token 和时间预算。任何阶段失败、取消或超限均保留先前结果并停止后续调度。

## 验证和恢复

模拟 Bug 先观察失败，再进行分析、开发和受限容器回归；回归结果按实际记录传入审查。写入任务完成 Agent 协作后仍停留在待用户检查，不将模型自述当成需求验收或自动合并。未发生代码修改、无测试或测试失败均不能报告为已修复。关联工作区任务目前不支持从检查点自动恢复；无工作区任务继续使用已有两角色安全恢复，不能伪装复用开发 Agent。

验收覆盖三角色顺序和依赖、角色工具权限交集、交接实际传递、预算不足时未执行后续角色、只读任务兼容和模拟 Bug 回归；使用模拟模型检查结构，真实 DeepSeek 和临时 Git 仓库做小规模端到端验证。当前仍不是模型动态生成的任意任务图、并行多 Agent 或可配置角色管理。
