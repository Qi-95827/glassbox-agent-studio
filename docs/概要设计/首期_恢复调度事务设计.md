# 恢复调度事务设计

## 问题与目标

恢复运行、计划和恢复事件必须一起落库；如果线程池明确拒绝恢复任务，原运行不应永久被一个确定未启动的子运行占用。保留失败子运行供审计，仅在确认未入队且失败状态成功落库后，允许用户从原检查点再次请求恢复。

## 状态与规则

为运行增加稳定的恢复派发状态 UNKNOWN／REJECTED。历史数据及普通运行默认 UNKNOWN；UNKNOWN 包括已经提交、尚未确认和进程异常等情况，必须保守阻止重复恢复。只在线程池同步抛出 RejectedExecutionException、确定未接受任务时，将仍为 PENDING 的恢复子运行以同一数据库事务标记 FAILED／REJECTED、跳过未开始节点并写失败事件；成功后解除本进程的父运行恢复标记。查询父运行是否已经恢复时，只忽略这种明确 REJECTED 的子运行，其他状态均阻止重复。该字段不推断模型或外部系统结果。

创建恢复子运行、计划和 RECOVERY_STARTED 事件同一事务，预算从父运行与检查点的较大消耗继承；提交成功后才尝试排队。若写失败、事件失败则回滚整个子运行并释放本进程标记。若进程在提交与排队之间崩溃或拒绝状态无法落库，结果保持 UNKNOWN、不得自动重复；仍需人工检查。工作区与 Bug 恢复限制不变，依旧不提供跨进程互斥、持久化队列或恰好一次。

## 验证

使用数据库故障注入确认恢复事件失败时无孤立子运行或计划；模拟队列拒绝，验证子运行保留为明确未启动状态，父运行可再次发起；确认普通已接受／未知子运行仍阻止重复，旧数据默认 UNKNOWN，预算与现有连续恢复回归不变。
