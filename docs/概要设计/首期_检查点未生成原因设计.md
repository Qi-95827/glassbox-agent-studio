# 分析后检查点未生成原因设计

## 目的与范围

分析成功不代表一定能安全地从审查前继续。对尚未支持恢复的任务，以及工作区一致性无法确认的任务，运行轨迹记录原因；任务本身仍按原流程继续，事件不代表运行失败。该说明仅针对分析后的恢复检查点，不代表运行中没有其他类型的检查点。

## 判定顺序

1. 不关联工作区和 Bug 的任务维持原有检查点逻辑。
2. 关联 Bug、允许写入或装配项目背景记忆的工作区任务，分别记录尚未支持的原因。
3. 符合只读条件时，比较分析前后的工作区指纹：任一时点无法可靠计算，或两次指纹不同，均跳过检查点并记录对应原因；一致才保存。
4. 事件只使用固定说明，不记录本地路径、文件内容、密钥或原始异常。历史运行不会补写事件；分析未成功时也不保证有此事件。

## 展示与边界

执行轨迹展示“未生成分析后检查点”和原因；中断任务的恢复区提醒用户查看轨迹。检查点结构有效不等于恢复时工作区仍然有效，申请及执行前仍须重新检查。该功能不能检测分析过程中的短暂修改后还原，也不提供外部副作用回滚或分布式一致性。

## 结构化记录与监控

事件另外保存稳定的原因枚举编码，说明文字可调整而不影响统计。Prometheus 输出按固定原因枚举聚合的数据库快照值，不含运行 ID、工作区、用户及路径；缺失或未知编码归入固定 UNKNOWN 类别，不将数据库中的任意值作为标签。历史记录不倒推原因。指标表示当前保留事件数，不是单调计数器；删除历史数据后可能下降。

项目 Grafana 看板预留该指标面板，并复用现有 Prometheus 数据源。工作台未运行或采集尚未发生时面板可能无数据，不应解释为事件数为零。
