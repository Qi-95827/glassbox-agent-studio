# 评测定义快照与对照设计

## 目的

对照历史评测时，套件名称相同并不证明案例输入和断言条件相同。每次批次创建时保存本次固定种子集的定义快照与摘要，在条件不一致或无法确认时，不把案例状态差异标记为改善或退化。

## 处理流程

1. 服务端构造固定套件快照：套件编码、断言语义版本、模拟模型、轮次和时间限制，以及每个种子案例的编码、标题、场景、工具上限和期望运行状态。运行所用的公共轮次与时间限制复用快照的同一组常量。
2. 批次和案例在同一事务创建，批次记录原始 JSON 与 SHA-256。页面可查看快照与摘要；快照不包含用户密钥或实际代码。
3. 比较两个批次时，先分别核对快照与自身摘要，再核对套件编码、快照内容和摘要。任一快照缺失、损坏或不同，逐案例的改善／退化结论均为无法判断，资源数据仍按已记录数据展示。
4. 历史批次没有快照时保留未知，不能推测成当前定义。尚未结束或没有结果的样本仍不能判定变化。

## 边界

快照记录列出的固定配置；不锁定项目代码、依赖、操作系统、模型实现或全部环境，也不证明运行可以复现。SHA-256 用于检测意外不一致，不是抗篡改签名。断言逻辑发生语义变化时开发者必须更新断言版本，系统尚不自动检测代码变化。当前仍是内置固定种子集，不支持用户管理数据集、真实仓库修复评测或自动归因。
