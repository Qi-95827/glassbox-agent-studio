# 连续恢复检查点设计

## 目标与范围

无工作区、无 Bug 的任务，从分析完成／审查之前的检查点恢复时，可在新运行中保存一个新的同阶段检查点；该新运行再次中断时，允许继续恢复审查，无须重复执行已完成分析。仍只支持用户手动恢复中断运行，且同一个父运行只能创建一个恢复子运行；不实现周期快照、框架会话恢复或外部副作用回滚。

## 引用与校验

原版检查点 v4 引用本运行完成的分析调用；新版 v5 保存来源运行 ID 和原分析引用，在每次恢复前验证来源位于当前检查点所属运行的祖先链、属于同一任务、分析确实完成且结果摘要匹配，以及当前计划的分析节点明确记录复用该来源 Agent。禁止循环父链、跨任务或跨祖先引用，损坏的引用不得恢复。摘要用于发现意外损坏和不一致，不是数字签名，不能防御能够改写数据库并重新计算摘要的攻击者。v3／v4 保持原有读取语义。新运行计划仍将分析标记 REUSED，真实模型调用和事件只属于实际运行；传递的工具证据指向真实来源运行。

恢复后的运行继续继承整个父链已发生的模型用量、轮次、工具调用和耗时，不能因连续恢复重置预算；父运行历史保留，新检查点与保存事件同事务。若审查调用已发起后进程中断，外部模型可能已执行并计费；再次恢复会重新发起审查，无法保证外部操作恰好一次。工作区、Git 和模拟 Bug 相关运行继续拒绝恢复，直至有外部状态对账。

## 验收与局限

模拟两次连续恢复，检查仅运行审查、源 Agent 与工具证据保持一致、预算不倒退及每层检查点有效；篡改引用、来源结果、跨任务和无关祖先必须拒绝。检查点和任务状态仍非完整全局原子事务：宕机发生在新检查点保存前，只能使用已经持久化的检查点，也可能存在在途请求结果未知。
